As the internet applications become omnipresent, log processing has become an essential component of the data pipeline. Kafka is a distributed messaging system that was developed at Linkedin for collecting and delivering high volumes of log data with low latency. It incorporates ideas from existing log aggregation and messaging systems.

There is normally huge amounts of log data produced, and it typically includes (1) **_user activity_** events corresponding to logins, pageviews, clicks, “likes”, sharing, comments, and search queries; (2) **_operational metrics_** such as service call stack, call latency, errors, and system metrics such as CPU, memory, network utilization on machines. There are many _**uses**_ for processing this data such as providing relevant search experience, recommendations based on item popularity, ad targetting, and security applications that protect users by identifying abusive behaviors such as spam or unauthorized data scrapping. 

The production systems that often creates this data is magnitudes of higher in size than the "real" data. China mobile collects 5-8TB of data every day. There are earlier systems built for processing log data, but they rely on scarping log files off of production servers. For example Facebook's Scribe or Yahoo's Data Highway, they are primarily designed for collecting and loading the log data for offline analysis such as into a Hadoop system. 

Some earlier messaging systems such as IBM Websphere MQ has transactional support that allow applications to write messages to queues **atomically**. Such _gurantees are not needed_ in our use cases and are an overkill for log data. Secondly they do not focus on _throughput_ as a primary design goal. For example JMS system do not have an API to allow producer to explicitly batch multiple messages into a single request. Third, these systems are not designed to be _distributed_, its difficult to partition and store messages on multiple machines. Fourth, these systems assume near immediate consumption of messages, which is the queues of unconsumed messages should not be long. Facebook's Scribe works like this: frontend machines send log data to Scribe machines and each of the Scribe machine aggregates log data and dumps it to HDFS cluster. This system uses _push model_, while Kafka chose _pull model_ to be more suitable. Pull model is efficient because each consumer can fetch messages at the maximum rate that it can sustain instead of getting overwhelmed by flood of messages. Also it allows to rewind the cunsumer to go back.

At Linkedin, Kafka greatly simplifies their infrastructure, since they can exploit a single piece of software for both online and offline consumption of the log data of all types.

# Kafka Architecture

A stream of messages of a specific type is called a **topic**. The producer can publish messages to a topic and these messages are stored at **brokers**. A **consumer** can subscribe to a topic and consume messages by pulling data from the brokers. A producer can choose serialization method to encode their messages and can send a set of messages in a single request. To consume messages, a consumer first creates one or more message streams for a topic and the messages published to that topic will be distributed to these _sub-streams_. Each stream provides an iterator to iterate over messages in that stream. Its possible to have point-to-point delivery, where multiple consumers fetch messages from a single copy of a stream or to have a publish/subscribe delivery where each consumer gets its own copy.
Kafka cluster consists of many brokers and to balance each topic is divided into multiple partitions. A broker can store one or more of these partitions.

## Efficiency on a Single Partition

There are some decisions that Kafka designers made to make the system efficient.

### Simple Storage

Each partition of a topic corresponds to a logical log. The log is a set of _segment files_ of approximately the same size. When a producer publishes a message, it is simple _appended_ to the last segment file. Messages are flushed to the disk in batches after some configurable messages are received, for efficiency. Consumers can only see the message after it is flushed. Messages do not have a __message_id__, instead each message is addressed by an __**offset**__ in the segment file. This choice avoids the overhead to maintain seek intensive random-access index structures that map the message ids to messages. To compute the message id of the next message, add the length of the current message to its id (read offset). 

Messages are consumed from a particular partition sequentially, if a consumer acknowledges a particular offset, it implies that the consumer has received all messages prior to that offset. Under the hood, the consumer is issuing asynchronous pull requests to the broker to have a buffer of messages ready. A pull request contains the message offset and the acceptable number of bytes to fetch. Each broker keeps a __sorted list of offsets__ in memory, including the offset of first message of each segment file.

### Efficient Transfer

As with the producer which can submit a set of messages in one send, consumer can also _retrieve multiple messages_ up to a certain size, typically hundreds of kilobytes in one PR. Another choice that they made is to avoid __**caching**__ messages at the Kafka layer, it relies on the page cache for caching of messages. This choice suits well here since OS __**page cache**__ can read ahead and fetch the sequential data from the disk prior to being asked. Also it uses write-through cache, for safely writing to disk. Additional benefit of having no Kafka level cache is that it has little overhead of memory garbage collection. This makes it suitable to implement Kafka in VM based language, i.e Java. 

Kafka also optimizes network access for consumers. A normal data flow to transfer message from a local file to remote socket looks like this: (1) read message __from disk__ to the OS __page cache__, (2) copy data from page cache to __application buffer__ (3) copy application buffer to __kernal buffer__ (4) send the kernal buffer to the socket. But Kafka uses sendfile API to directly transfer bytes from file channel to socket channel. This avoids copying between application buffer and then to kernal buffer. 

### Stateless Broker

Kafka does not keep the information about __how much messages are consumed__, instead this is maintained by consumers. This reduces complexity but makes it hard to delete the messages since Kafka is not aware if all consumers have consumed the messages. To solve this, Kafka has this time based __retention__ policy, after which a message is automatically deleted if it has been retained longer than the configured period (7 days etc). Since the performance of Kafka does not degrade with large data, this makes the retention of messages possible.

Another benefit of not deleting messages is that the consumer can __rewind back__ to an older offset for any reason. This feature is essential for some applications, e.g if the consumer app has a __bug in its logic__ then it can replay messages after the bug is fixed. For a data warehouse where data is only flushed to disk after some period, if the consumer __crashes__, unflused data is lost. To avoid this, the consumer can checkpoint offsets and re-play from the last checkpoint when it restarts.

## Distributed Co-ordination

A producer can either publish message to a randomly selected partition or a parition selected by a partition key and a partitioning function. This is similar to a sharding key e.g __user_id__ or __likes__. Partition = hash(key) and take modulo of total_no_of_partitions. Lets say there are 4 brokers `0 1 2 3` and _likes_ is the key. Then the process is like this:

```
parition = murmurHash2(likes)%4
```

This way parition is determined and then then the responsible broker is determined by checking the leader for that partition.

Kafka has __consumer groups(C groups)__, they consist of one or more consumers that jointly consume a set of subscribed topics. A message is consumed by only one of the conusmer within a group. Different C groups idependently consume messages and no co-ordination is needed between different C groups.

Kafka wanted to _divide messsages_ on brokers evenly among consumers. To achieve this it introduced _partition as the smallest unit_ of parallelism. This means two consumers from the same C group can not ingest messages from a single partition at the same time. If it is allowed then the consumers would have to co-ordinate among themselves to who has consumed what, and also the locking overhead. Instead, the only time the consumers have to co-ordinate is when rebalancing the load. This is not as frequent as consuming messages itself.

Another decision is to __not have a central master__ node, and instead let the consumers co-ordinate among themselves. This avoids us to think about the master failures, further complicating the system. To facilitate co-ordination among consumers, Kafka utilizes Zookeeper. Its a consensus based service with filesystem like API [Zookeeper](/_posts/2026-03-12-apache-zookeeper.md). Zookeeper replicates data and is highly available with strong consistency.

- When a broker/consumer starts up they store their information in a broker or consumer registry in zookeeper. _**Broker registry**_ contains the broker's hostname and set of topics and partitions stored on it. The _**consumer registry**_ stores C group it belongs to and the set of topics it subscribes to.
- The _**ownership registry**_ has one path for every subscribed partition and the path value is the consumer_id currently consumig that partition. 
- The _**offset registry**_ has one path for each subscribe partition and the offset of the last consumed message in the partition.

> The Zookeeper nodes are ephemeral for all registries except offset registry which is persistent. So if a broker dies then all the partitions stored on it are automatically removed from Broker registry. And if consumer dies, then its entry from the ownership/consumer registry is removed. Consumers registr a ZK watcher to get notified when a change happens in consumer or broker registries. Consumer first finds the set of available partitions for a topic and a set of consumers which are subscribing to topic. Then it range-paritions into chunks and deterministically picks one chunk to own.

Each consumer when picks a partition to consume, it writes itself in the ownership registry and then starts a thread to fetch messages starting from the offset in the offset registry for that partition. After pulling messages, the consumer updates the offset registry **periodically**.
Basically co-ordination of how much messsages are consumed is stored in offset registry and its persistent. This is how consumers know the state of the consumed messages.

When there are multiple consumers within a C group, each is notified when a consumer/broker changes. But the notifications might come at different times at different consumers. In this case, two consumers might try to own a partition which is still owned by another consumer. When this happens, the first consumer releases all the partitions it owns and and waits a bit before retrying the rebalance process. The rebalance process stabilizes after few retries.

## Delivery Guarantees

Kafka only guarantees _**at-least once**_ delivery. Since the exactly once guarantee requires two phase commit and is not required in our use case. Often the message is delivered exactly once, but in a case when a consumer crashes without commiting the latest messages it consumed in the Zookeeper, then the new consumer may get the messages twice. If an application is sensitive to duplicates then it should add de-duplication logic, using offsets returned to consumers or using a unique key within a message.

Kafka guarantess __ordering on the messages within a partiton__, but it does not give any guarantees on the ordering of messages from different partitions.

To deal with data corruption, Kafka writes CRC along with a message in the log. Having a CRC on the message level, allows to check for network errors after a message is consumed/produced. 

If a broker goes down then the messages stored on it become unavailable, or if the storage system on a broker is permanently broken then the unconsumed messages are lost forever. Developers plan to add built-in replication in Kafka for future.


## Summary
- A stream of messages of particular type is called a topic, Producer writes to a topic, and these messages are stored at Brokers
- Point to point delivery: many consumers consume one copy of all messages in a topic, Publish Subscribe: each consumer has its own copy
- Simple storage: Topic divided in partitions, each partition is stored as a log file by appending to it. Messages identified by offset, Broker has sorted list of offsets.
- Efficient Transfer: Consumer sends PR with offset, Kafka transfers using file-api of Linux to transfer efficiently
- Stateless Broker: broker does not track the consumption, reduces overhead. Consumer can rewind to old offset if it crashes/flushes periodically data to disk.
- partition is smallest unit so one consumer takes on one partition in a consumer group
- No central master and instead consumers co-ordinate among themselves
- Broker, consumer, ownership and offset registry in Zookeeper
At-least once guarantee and messages delivered from one partition in order
