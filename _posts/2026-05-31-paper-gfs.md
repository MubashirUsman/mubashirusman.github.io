GFS goals were to design a distributed file system which has high performance, is reliable, available, scalable. In addition it assumes the following points. 
1. Component failures is a norm rather than exception, therefore monitoring, error detection, fault tolernace and recovery should be built in.
2. Files are huge by traditional standards, multi-GB files are common and system is not designed for billions of KB-sized files.
3. Most files are mutated by appending new data rather than overwriting the existing data. Random writes are almost non-existent, once written files are mostly read sequentially.
4. Designing both the applications and file system API gives Google flexibility and benefits overall design. For example atomic append exists to allow multiple clients to concurrently can append without extra locking mechanism.

## <span style="color:#005385">Design Assumptions<span>

 - Uses commodity hardware that fails often, therefore detection, tolerance & recovery are essential
 - Stores a few million large files (100 MB to multi-GB); multi-GB is the common case
 - Workloads: large streaming reads + small random reads
 - Large sequential writes that append to files; once written, files are rarely modified
 - Many producers concurrently append to a file (producer-consumer queues, merge results)
 - High sustained bandwidth > low latency; bulk throughput matters more than per-op latency


## <span style="color:#005385">Interface</span>

Familiar file system API (not POSIX). Files organized hierarchically, identified by path names.
Standard operations: `create, delete, open, close, read, write`
Snapshot — creates a copy of a file or directory tree at low cost (copy-on-write)
Record Append — multiple clients append to the same file concurrently while guaranteeing atomicity of each individual append; avoids distributed lock managers

## <span style="color:#005385">Architecture</span>

### <span style="color:#ADD8E6">Components</span>

| Component     |	Role |
|---------------|--------|
| Single Master	| All metadata; chunk placement decisions; no involvement in data         |
| Chunkservers	| Store chunks as plain Linux files; serve reads/writes directly to clients   |
| Clients	    | Linked with GFS library; contact master for metadata, chunkservers for data |

> Neither client nor chunkserver caches file data. Clients cache metadata only. Linux buffer cache on chunkservers keeps hot data.

### <span style="color:#ADD8E6">Single Master</span>
 - Single master vastly simplifies the design; master makes sophisticated chunk placement decisions with global knowledge
 - Must minimize involvement in reads/writes to avoid becoming a bottleneck
 - Client asks master for chunk handle + replica locations, then contacts chunkserver directly
 - Client caches this info for a limited time and for multiple subsequent operations
 - Client can ask for multiple chunks in one request; master can piggyback nearby chunk info

### <span style="color:#ADD8E6">Chunk Size: 64 MB</span>

This chunk size is much larger than typical FS block sizes. Chunks are stored as plain Linux files on chunkservers; lazy space allocation avoids internal fragmentation.

#### **Advantages**
- Reduces client-master interactions
- Client can keep an open TCP connection to the same chunkserver for a long time
- Reduces metadata stored on the master
- Large chunk = more operations on same chunk = persistent TCP connection savings

#### **Disadvantages**
- Hot spots can form: small files consist of one chunk; if many clients access it simultaneously, chunkservers become overloaded (mitigated by higher replication factor). Another solution would be to allow clients to read from other clients.

## <span style="color:#005385">Metadata<span>
### Three types

| Type	| Storage  |
|-------|----------|
| File & chunk namespaces | In-memory + persistent on disk (operation log) |
| File-to-chunk mapping	  | In-memory + persistent on disk (operation log)
| Chunk replica locations |	In-memory only — polled from chunkservers at startup & HeartBeat|


### In-Memory Data Structures
All metadata on master is kept in RAM, thus master ops are fast; it also makes easy to do periodic background scans for GC, re-replication, chunk migration. The limitation is that there is just so much you can store in memory and so the capacity of the system is limited by the RAM on master. But since master maintains approximately 64 bytes metadata per 64 MB chunk, it is practical even for large clusters; not a serious limitation. Namespace data requires less than 64 Bytes per file using prefix compression.

### Chunk Locations

Chunk location information is not persistent on master, it just polls this information at startup and stays updated via HeartBeat. The reason for polling is that it removes the need for keeping the CS and master in sync as the CS come and go. Another reason is chunkserver has the final word on what chunks it holds, because there are many reasons why chunk locations can change, e.g errors may cause chunks to vanish spontaneously.

### Operation Log
Operation Log is the critical information of state changes of GFS, its persistent record of metadata and state of master. It also serves as a logical timeline for concurrent operations as it gives a global order to write operations. Files, chunks, and their versions are identified by logical times of creation.
Operation log must be stored reliably, its replicated on multiple remote machines; changes are not visible to clients until log record is flushed to disk locally and on all replicas. Master recovers its state by replaying operation log and therefore for faster starts this log should be small. This is where **checkpoints** comes in.
Master batches several log records before flushing, it reduces impact of flushing/replication on throughput.

- Master checkpoints state when log grows beyond a threshold
- Checkpoint is a compact B-tree form directly mappable into memory — used for namespace lookup without extra parsing; this speeds up master recovery
- New checkpoint created in a separate thread without delaying incoming mutations

> Recovery: load latest checkpoint from disk, then replay only log files after that checkpoint.

## Consistency Model

File namespace mutations (file creation) are atomic, master's operation log defines global total order of these operations. The state of a file region depends on: 1) type of mutation 2) whether it succeeds or fails 3) whether there are concurrent operations
| Term | Definition|
|-|-|
| Defined    | Consistent AND clients will see what the mutation wrote in its entirety |
| Consistent | All clients see the same data regardless of which replica they read |
| Undefined  | Consistent (same data across replicas) but may be mingled fragments from multiple mutations |
| Inconsistent | Different clients may see different data at different times |

| Operation | Result |
| ----------| -------|
| Write/Append with NO concurrent | Defined |
| Write with Concurrent | Undefined but consistent | 
| Append with concurrent | Defined, interspersed with inconsistent |

Primary chunkserver defines the order of operations for all followers.

All serial writes and appends are *Defined*. But concurrent writes leave regions *consistent and undefined* because the data may end up mixing or interleaving, for example if there are three write requests at the same time to mutate a file, then primary might break the write requests in a way that end up interleaving on all replicas.
For example, if Client 1 tries to write AAAA and Client 2 tries to write BBBB to the exact same offset at the same time, the primary chunkserver might order the fragments like this: AABB. The primary will force all replicas to write AABB. It is consistent because every single replica has AABB. It is undefined because neither client's write is visible in its entirety. The data is a mixed jumble.


Record append is atomic append and it results in *defined and inconsistent* regions. Record append ensures it happens on a single chunk and not on two chunks, this can leave some white spaces in between, it can also leave some regions to have duplicate data if there was a retry and the first try succeeded on one chunk server but not the other.
For example, if an append succeeds on the primary and Replica 1, but fails on Replica 2, the client retries. The primary will pick a new offset further down the line. This leaves the first attempt's data as a "duplicate" on the replicas where it initially succeeded, resulting in a region that is defined interspersed with inconsistent.

GFS offers loosly defined/consistent data with some interspersed inconsistent data.

After a series of successful mutations the region is guaranteed to be defined and contain data written by last mutation, GFS achieves this 1) by applying the mutations on all chunk servers in same order 2) using chunk version numbers to detect any replica that has become stale because it has missed mutations when the chunkserver was down.

GFS identifies failed CS by exchanging regular heartbeat messages with chunkservers.

### Implications for the applications

GFS handle relaxed consistency model by some techniques. Applications mutate files by appending rather than overwriting. Apps atomically rename the file after writing all the data, it can checkpoint how much has been successfully written. Readers verify and process only the regions that have been wwritten in defined state. Readers deal with padding and occassional duplicates as follows: a reader can identiy and discard extra padding and record fragments using checksums. It can also filter duplicates out using unique identifiers.

## System Interactions

### Leases and Mutation Order

Master issues leases to Chunkserver and that chunkserver becomes a primary, primary uses serial numbers to set mutation order within a lease. So the global mutation order is set by lease and serial number within a lease. Lease is extended via heartbeat messages.

> Data Flows like this: 1) client asks master for primary and replicas 2) the master replies with the locations of primary and secondary replicas and client caches these results 3) client pushes data to chunkservers in a **linear order**, means from its neareast server to chunkservers 4) after getting the acknowledgement from replicas, client sends a **write request to the primary** and this request is assigned a serial number by primary. After that primary forwards request to secondary replicas 5) Secondaries reply to primary and then primary replies to the client

GFS decouples data flow from control flow to use network topology to the fullest. To avoid network bottleneck, each machine forwards data to its closest machines that has not received it. Latency is minimized by pipelining data transfer over TCP connections, and once a CS has received some data it starts forwarding immediately, this is possible because GFS uses network with full duplex links.

E.g Network throughput `T` is typically 100Mbps and latency **L** between two machines is below 1ms, so for transferring `B` bytes to `R` replicas `t = B/T + R*L`.
```
Troughput = 100*100^6/8 = 12.5*10^6 B/s = 12.5MB/s
Replication overhead = R*L = 3*1ms = 3ms
time t = 1*10^6 bytes/ 12.5*10^6 = 0.08 seconds = 80ms

That is 1MB can be be distributed in 83ms.
```

### Atomic Write Appends

Concurrent writes to the same region are not serializable, the region may end up containing data fragments from multiple clients. In a record append client specifies only data (GFS chooses where to put it) and GFS appends it at-least-once atomically similar to how UNIX does when O_APPEND flag is set. GFS checks if the data can fit in the current chunk size (64MB) and if can not fit, it tells the client to retry on the next chunk. If the data fits in the max size, primary writes and tells the secondaries to write at the same offset. **GFS guarantees that data is written at-least-once as a unit.**

### Snapshot

The `snapshot` operation makes a copy of a file, it uses **copy-on-write** technique and that's why it happens almost instantaneously. Uses of snapshot feature are in copying data or checkpointing the current state.

When a master gets a snapshot request, it revokes outstanding leases for the chunks of the files, this is to make sure that subsequent writes will go through the master. The master logs the operation to disk, then it duplicates the metadata of the file and this file points the same chunks as original files, master also increments reference count to the chunks. 

If a write request is received, master defers replying to client and asks the CS to create a copy `C'` of the chunk `C` locally. Copied locally as the disk throughput is about 3 times than the ethernet (Mbps).

## Master Operations

### Namespace Management and Locking

Designers of GFS did not want to slow down important operations running already on master for operations that take long, such as snapshot. For this it uses locks on regions of namespaces for allowing multiple operations. GFS namespaces are not like that in normal Linux OS filesystem, i.e there is no dentry, or symlinks. It uses flat mapping between full pathnames and metadata. All pathnames (could be just filename or an absolute directory) have an associated read-write lock.

The read lock on the directory name prevents the directory from deletion, snapshot or rename. The write lock prevents two files with the same name from being created.

> For example: Locking will prevent creation of `/home/user/foo` file while `/home/user` is being snapshotted to another path `/save/user`. Because snapshot acquires read lock on `/home` and `/save` and write lock on `/home/user` and `/save/user`. But file create acquires read on `/home/user` and write lock on `/home/user/foo`, these are conflicting locks and will be serialized properly. This just means two operations are not trying to acquire the same lock.

File creation acquires a read lock on parent directory and a write lock on the file. It does not require a write lock on parent directory, because there is no directory/inode like data structure which needs protection from modification. 

**To prevent deadlock:** Locks are allocated in consistent total order: first ordered by the level in the namespace and then lexicographically at the same level.

### Replica Placement

GFS is spread on many machines across racks. Bandwidth(BW) into and out of racks may be less than the aggregate BW within the same rack. Spreading replicas across machines prevent a disk or machine failures. But to prevent against rack failure we need to spread across racks. Chunk placement servers two purposes: availability and maximum network bandwidth utilization. So the goal is to spread replicas across machines and also spread across racks for availability.

Benefit is that read traffic will get to exploit the aggregate bandwidth of multiple racks, but tradeoff is that writes will have to go through many racks.


### Creation, Re-replication and Re-balancing

The **creation** of replicas takes into account three factors: (1) we want to place new replicas on CS with below average disk usage (2) we want to limit the _recent creations_ on our CS (3) we want to spread the replicas across machines and racks.

As the number of replicas fall below the desired number, master **re-replicates** the chunk. It could be due to CS failure, corrupted chunk, failed disk, desired goal is increased. Re-replication takes into account two factors: how far the replica count is from the desired count, a chunk losing 2 replicas will get priority over a chunk losing 1. Live files are replicated before replicating deleted files. If a chunk is blocking client progress then its priority is boosted. The master clones the chunk by asking CS to get the data for that replica from exiting replica. The goals are same as for creation to consider disk usage, to limit active operations and spreading across racks. Also CS throttles its read request to prevent the source from overwhelming due to cloning.

Master does **Rebalancing** periodically, master analyses current distribution and moves replicas around for the same goals as in creation: better disk usage and load balancing. This is the process through which master fills up new CS, instead of instantly sending new chunks and heavy write traffic.

### Garbage Collection

When the file is deleted, GFS does not immediately reclaims the space, it does so only lazily during regular garbage collection for both files/chunk levels.

When a file is deleted, master logs the operation and rename the file to a hidden name with the timestamp. During the normal scan of the namespace, such file name is deleted if it has existed for more than 3 days. Until this time the file exists and can be read under new name. How are chunks deleted on CS? In a regular _Heartbeat_ messages, CS reports the chunks it has and master replies with the identity of chunks that are no longer existed on master and then CS is free to delete at its own.

Even though distributed GC is hard, its easier in GFS's case, this is because master can identify all references to chunks as they are in the file to chunk mapping. Also chunk repicas are Linux files on CS and any unknown files are "garbage". 

This way of GC is simple and reliable at large scale, where components can fail at any time. Heartbeat messages are better than eager deletion as deletion messages may be lost during sending and then they will need to be sent again. **Advantages** GC provides a uniform and dependable way to clean up replicas not known to master. 
1. It also merges the problem of storage reclamation into regular background activity of master. 
2. GC is done only when master is relatively free. The master can respond to clients promptly where master's attention is needed.
3. It provides safety against the accidental deletion.

A big **tradeoff** of this type of GC is that it hinders the user to tune for storage when storage is low. For apps that create and delete files more often, they may not be able to delete. This is overcome by expediting the deletion of the file, if its deleted again. Also GFS allows users to set replication and reclamation policies to different namespaces. So files will be stored without replication. They will also be deleted immediately and won't be recoverable.
