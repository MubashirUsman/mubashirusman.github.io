Dapper was developed at Google for tracing the application's activity throughout the request response cycle.
# The Problem
Lets say a Google search queries many services to get a response, then an engineer looking at the latency may not know which service is causing the latency. There could be many reasons for this: the engineer is not aware of the services involved, he is not expert in each service, a resource might be shared by multiple services such as a database.

The fundamental requirements for Dapper are: (1) ubiquitous deployment, (2) transparent to applications and (3) low overhead. (4) scalable and should make the tracing data quickly available.
1. Ubiquitous because every part of system needs monitoring.
2. Low overhead because monitoring system should not impact the performance of the running services.
3. Transparent to application because it becomes prone to bugs if application developers have to collaborate to use it.

## Design Decisions 
Low overhead is achieved by selective sampling and application level transparency by restricting instrumentation to core threading and RPC libraries. The instrumentation is low enough that even Google search can be traced without additional annotations.

# Distributed Tracing in Dapper

Annotation based schemes tag each record with a global identifier. This identifier links the message back to the originating request. Black box methods assume there is no additional information than the message, and use regression to gain insight. The problem with annotation based methods is the need to instrument the applications. But google could avoid it fortunately because it could get away by instrumenting COMMON LIBRARIES.

In Dapper traces are modeled with **trees and spans**. Spans are nodes of the tree. Each span contains a __span_id, parent_id and span_name__ to form a causal relationship. IDs are 64bit ints and each RPC gives out a single span. A span contains information such as start and end time and can contain information from multiple hosts such as client and server. The timestamps will come from different machines so be careful of the clock drift. This is catered by the fact that client sends a request before server responds so the lower/upper bound on RPCs server side is considered.

## Instrumentation and Application Annotations

Instrumentation points are **(1) threads (2) async callbacks (3) RPC calls**.
Trace Context(a cotainer containing span_ids etc) is attached to a thread. Callbacks in async computation also store the trace context and they are attached to the callback when invoked.
In dapper a framework that is used by nearly all services is instrumented to define spans for all RPC.

In addition to the above trace points, developers can also add additional information to traces. This is done by exposing an API which gets the current trace and can add information. This information could be textual or can contain map of key-value pairs. But trace spans have an upper bound on total annotations. This upper limit is to protect Dapper from too much logging. The map of key-value is useful for keeping counters or keeping other information. At this point I feel these features are some next level shit which are beyond logging and black box metrics monitoring.

## Trace Collection

Trace collection: This pipeline consists of (1) writing spans to local log files (2) pulling the data by Dapper Daemons (3) from Dapper daemons its written to BigTable rows. Each trace is a row in Bigtable and each column is a span.

The latency of collection at 98 percentile is less than 2 minutes for 75% of the time. But it can take hours for remaining 25% of time.

Dapper's trace Logging and Collection is decoupled for two reasons. First, sending data back in RPC response can impact application response time. Second, all RPC systems are not perfectly nested, means that some apps return results even when their own backend have not responded. Therefore they are not properly nested. For security reasons, Dapper only includes the RPC method name without payload in logs.

# Dapper's Deployment

Dapper's most important part is instrumentation of common RPC and threading library. It should be lightweight, robust and stable.  This library is responsible for creation/sampling/storing of spans on lock disk. This code is only 1000 lines of C++.

The dapper consists of components: 1) the apps that generate Dapper traces and 2) the trace collection Dapper daemons. Dapper daemons are part of Google's base machine image.

Sometimes Dapper is unable to follow the control path correctly, mainly due to use of non-standard control flow primitives and when Dapper mistakenly attributes causality to unrelated events (I don't know what this means). In addition, Dapper offers a library for applications to manually trace events. Sometimes service owners turn off Dapper tracing, reason being the monitoring overhead, though this is rare.

Some applications (infact 70% of all spans) contain custom application specified annotations. Apps do this to understand intra-span activity.

Managing overhead of tracing: the tracing's cost is considered as performance degradation because of trace generation and for the storage needed to store traces. So the focus is on low overhead. Total overhead = Overhead of trace creation, overhead of trace collection, overhead of impact on production workloads. Dapper uses adaptive sampling to mitigate this.

Trace generation overhead is due to library creating a span and destroying it, it takes around 204 nanoseconds to create root spans and 176 ns for non-root spans. The cost of additional annotations such as textual/string is around 40 ns. The local disk writes in dapper's library are most expensive especially if all requests are traced.
