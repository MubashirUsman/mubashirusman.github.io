# Chapter 19 Load Balancing at The Frontend

The scale which Google operates on, which serves millions of requests/s, a single computer can not serve their purpose no matter how huge that computer might be. Even if it exists, it will be a single point of failure.

Load balancing at the frontend means how to distribute requests at the __global__ level __between datacenters__. Before distributing the requests, the nature of the request needs to be understood. For example a __search query__ needs to be served fast while a __video upload__ request does not have to be fast but should succeed at the first attempt. In the first case RTT is the critical factor and therefore the request should be routed to nearest datacenter and in the second case throughput is the deciding factor and therefore should be routed to a datacenter which is underutilized (NOT saturdated). Load balancing within a datacenter does not take into account the distance, instead it focuses on optimal resource utilization.

## Load Balancing using DNS

Since every request has to lookup DNS, its the first level to balance load. Simplest approach for DNS load balancing is to return __multiple A or AAAA__ records and client can pick one address. 

- The challenge here is that the clients __pick IPs arbitrarily__ and will not consider server side load. It will lead to each IP receiving equal amount of traffic. In theory it can be mitigated by __SRV records__ by assigning weights to each IP, but SRV records are not supported by HTTP clients (browsers).

- Another problem here is that __clients do not know the distance__ from each IP or which one is nearer to them. This can be mitigated by using __Anycast__ address for authoritative nameservers (A-NS) and the DNS queries will flow to the closest datacenter. This is not very trivial, as A-NS rarely talk to the end user, because a __recursive NS__ queries the IPs on behalf of the client. Therefore the closest NS is closest to the recursive NS and NOT the client. This is the limitation and Anycast only optimize for the distance between resolver and the A-NS. This problem of recursive NS could be solved by using `EDNSO` extension which allows to include the __client's subnet__ address in the DNS query.

- Another problem is that Recursive-NS cache responses for a given TTL period, and estimating the impact of the reply is difficult. To estimate this impact Google updates its list of known DNS resolvers and the __number of users behind__ them. Another estimate they make is to __track the geographical location__ of users behind a resolver. If the user base is distributed across regions then the trade off is made to optimize for the region with more users. But DNS load balancing does not stop there, in fact there are other factors to be taken into consideration: traffic, capacity and network connectivity among few to keep the Authoritative NS up to date.

Despite of these problems, DNS load balancing is still simple and effective way to distribute traffic before even the connection starts.
> All DNS replies should be less than 512 bytes, the limit set by the RFC 1035. And therefore it limits the number of addresses that can be included in the response.

As an example, lets say different datacenters advertise the same address for a mail service. Then why would you include multiple IPs in a DNS response? The answer is even when multiple datacenters advertise the same address, still there should be more than single datacenter with different IPs in the same region. So multiple datacenters with different IPs, and those IPs still yet are anycasted. 

## Load Balancing with Virtual IP Address

Virtual IP(VIP) are not assigned to a single network interface, instead it is __shared among many machines__. This hides the implementation details, such as how many machines share a single IP and for upgrading/adding/removing of machines without users can notice. For this, a device called _Network Load balancer (NLB)_ is used, which receives a request and sends it to one backend.

But to which backend NLB should send a given packet? The answer is to a server with least load. This is nice for stateless protocols, but what if the request depends on previous request i.e stateful protocols. Stateful workloads need to use the same backend for the duration of the request. Then this logic breaks, one workaround is to forward request to the same server and keep track of each connection. There is an alternative to avoid keeping the state in memory. It is to use some information of a request to calculate a connection ID using a hash function, and use that to choose a backend. This means all connections will need to be reset when a server is removed/added.

```
id(packet) % N
N is the number of backends, id is some sort of hash function
```

This will always send a request to the same backend. But if the N changes, it will produce entirely different output. There is another __alternative to hashing__ called __consistent hashing__. It does not require to keep the state of every connection in memory and also does not force the connections to be reset. Consistent hashing provides a mapping mechanism that does not require to reset connections even when new servers are added or removed.

How exactly does the NLB forwards packet to a backend. One approach is to _use NAT_, but NAT does require to keep __track of network connection__, which is clearly the violation of having a completely stateless backend.

Another approach is to _change_ the __destination MAC address__ of the forwarded packet. This leaves all the information above the data link layer intact. Keeping this information intact has an advantage of sending reply by the server directly to the client. This technique of sending a direct reply to the backend is called _Direct Server Response_. And this solution has benefits that a small fraction of traffic needs to travel through the load balancer, and avoids keeping state in the NLB. For this solution to work, all machine must reside inside a _single broadcast domain_.

The current technique used by Google for VIP load balancing is __packet encapsulation__. The packet encapsulation works like this, NLB puts an incoming packet into another IP with General Routing Encapsulation(GRE) and uses backend's address as the destination. This means one layer above IP layer. When backend receives the packet, it strips off the IP+GRE and treats the packet as if it received the packet directly with the inner IP. The removes the limitation of broadcast domain. But the problem is it increaes packet size. This means packet has to be fragmanted if it exceeds the available Maximum transmission unit size. But once the packet reacher the datacenter, fragmantation can be avoided by using larger MTU.

> The summary of the chapter is to do load balancing early, and do it often. Early at the DNS level and then at the VIP using Network load balancer.
