Topic: Persistence — Disks, Databases, and the art of not losing data

1. The Fundamental Tension

Persistence is important — you cannot afford to lose data. But disk is slow. The goal is to achieve both: data that survives power outages and systems that feel fast.

Key Insight
We want persistence and speed. These two goals conflict — and the rest of this lecture is about how to reconcile them.

2. Databases & The OS Lie

Buffered I/O

When a process calls write(), the OS does not immediately write to disk. Data goes to the page cache (in RAM), and write() returns immediately. This is the "OS lie" — your data isn't on disk yet.

Buffered I/O flow

fsync() — Safe but Slow

fsync() blocks the process until writes actually reach disk and are confirmed. It is the antidote to the OS lie, but it is expensive — the process cannot proceed until the disk acknowledges the write.

Trade-off
Buffered I/O (fast, unsafe) vs. fsync() (safe, slow). The choice depends entirely on how much data loss your use-case can tolerate.

3. Write-Ahead Log (WAL)

Databases use a clever trick: instead of writing directly to the table (random I/O), they append every write to the end of a log file first. This is the Write-Ahead Log.

When the system is idle, it then updates the actual tables from the log. This converts random writes into sequential writes — and sequential writes are dramatically faster on both HDDs and SSDs.

Why sequential > random
On HDDs, the read/write head needs to physically move. Appending to a log = head stays still. On SSDs, internal management also benefits from sequential patterns.
Sequential writes > random writes.
Write-Ahead Log flow

4. SSD Internals — Write Amplification

A common misconception: SSD is not fast RAM. SSDs have a fundamental limitation: you cannot overwrite or delete a single byte. You can only erase in large chunks (typically ~2 MB blocks).

Flash Translation Layer (FTL)

The Flash Translation Layer is a small, smart orchestrator embedded in every SSD. It manages the physical erase blocks, tracks which logical blocks map to which physical cells, and handles the wear leveling so the drive doesn't burn out one area prematurely. It makes the drive look like a simple byte-addressable device — hiding all the complexity above.

5. B-Tree — Shallow and Fat

Reading sequentially is slow on disk. Without an index, every query is a full table scan. The B-Tree solves this: it is optimized for reads, keeping itself as shallow as possible by making each node very wide (many children).

6. LSM Tree — Log-Structured Merge Tree

The B-Tree is optimized for reads. The LSM Tree makes the opposite bet: optimize for writes. It is the engine behind NoSQL databases like Cassandra and RocksDB.

The key insight: only do sequential writes. Never do random writes on disk.

How LSM Works

Bloom Filter
A space-efficient probabilistic data structure. For each SSTable, the Bloom filter can say "definitely not here" (skip it!) or "maybe here" (check it). This avoids expensive disk reads for keys that don't exist in a given SSTable.

7. The RUM Conjecture

A fundamental trade-off in data structure design: you can optimize for any two of the three, but not all three simultaneously.

RUM Conjecture — pick any two
Read-heavy workload → Use B-Tree (e.g. banking, relational databases) Write-heavy workload → Use LSM Tree (e.g. logs, event streams, Cassandra)

8. The Invisible Enemy — Bit Rot

Even at rest, data can silently corrupt. Cosmic rays, voltage fluctuations, and magnetic interference can flip bits without the OS knowing. Do not trust hardware.

The solution: checksums (e.g. SHA-256). Compute a hash when writing data; recompute and verify when reading. ZFS, the filesystem, does this automatically for every block.

Disk Failure Rates

Statistically, out of 10,000 disks, approximately 1 fails per month. At scale (thousands of servers), disk failures are expected daily events, not exceptional ones. This forces distributed systems to treat failure as the norm, not the exception.

2003 — Google File System (GFS)
GFS splits data into chunks, storing 3 copies across 3 machines on 3 different racks. If one rack fails (power, network), data survives on the other two. But this introduces a consistency problem: all three replicas might have slightly different data at any point in time. Consensus protocols like Raft solve this.

9. The Big Trade-Off Spectrum

Every persistence decision sits somewhere on a spectrum between maximum speed (high risk of data loss) and maximum durability (slower speed).

Practical Examples

Example — Social media like
A user likes a post. If they see the like count update 2–3 seconds late, that is fine. Use an LSM tree with buffered I/O. Optimize for throughput.
Example — Bank transfer
A user sends money. Data loss is unacceptable. Use fsync() and wait for all replicas to acknowledge before returning success. Optimize for durability.
